# OMP publisher seams — scout report (S1, 2026-07-04)

Source: explore agent `OmpPublisherSeams` mapping vendor/oh-my-pi for the control-plane OMP publisher (spec v1 L1 adapter). Consumed by M1 packet P4.

## Summary

Mapped OMP extension loading, hook/event surface, model-call telemetry, session identity/fork semantics, import constraints, and prior observability paths. Key answer: an extension can subscribe with pi.on(...), can observe assistant message_end/turn_end for final AssistantMessage.usage/duration/stopReason, and can observe/replace provider payloads through before_provider_request for most built-in providers, but extension hooks are not a stable per-call ledger API with guaranteed raw HTTP headers/body across every provider.

## Full map

Q1 EXTENSIONS — discovery/loading/lifecycle
- Main path discovery is `discoverSessionExtensionPaths`: explicit `additionalExtensionPaths` plus `settings.get("extensions")`, unless `disableExtensionDiscovery`; disabled IDs come from `settings.get("disabledExtensions")` (`sdk.ts:712-722`). CLI `--extension` and legacy `--hook` are copied into `options.additionalExtensionPaths`; `--no-extensions` clears them (`main.ts:900-913`). CLI extension package dirs are also injected for sibling resource discovery (`main.ts:980-992`).
- Native discovery scans `.omp/` in the project and the active user agent dir from `getAgentDir()`; provider description says “Native OMP configuration from ~/.omp and .omp/” (`discovery/builtin.ts:1-36`). For extension modules specifically it discovers `<configDir>/extensions` and settings `extensions` entries (`discovery/builtin.ts:449-555`). `SOURCE_PATHS.native.projectDir` is `.omp`, and native user paths use `getAgentDir()` (`discovery/helpers.ts:27-35,94-108`).
- Extension package roots for sub-discovery are, in precedence order: CLI injected roots, project `.omp/settings.json#extensions`, user `~/.omp/agent/settings.json#extensions`, and enabled installed plugins; only directories survive (`discovery/omp-extension-roots.ts:1-18,35-65,113-171`). The companion provider scans package sibling `skills/`, `hooks/pre|post/`, `tools/`, `commands/`, `rules/`, `prompts/`, `.mcp.json` (`discovery/omp-plugins.ts:1-16,35-300`).
- Installed plugins are discovered under plugin `node_modules` plus `omp-plugins.lock.json`; their `package.json` `omp` or legacy `pi` manifest can declare `extensions`, and `resolvePluginExtensionPaths()` feeds those into extension loading (`extensibility/plugins/loader.ts:1-15,47-113,190-243,244-326`).
- Entry-point rules: configured path to a file is loaded directly; a directory can have `package.json` with `omp.extensions`/`pi.extensions`, or `index.ts`/`index.js`; otherwise one-level `*.ts`/`*.js` and subdirectories with package/index are scanned. No recursion beyond one level (`extensibility/extensions/loader.ts:337-449`).
- Entry-point signature: module itself or default export must be a function; loader calls `await factory(api)` where `api` is `ExtensionAPI` (`extensibility/extensions/loader.ts:39-45,278-311`). README example shows `export default function (pi: ExtensionAPI) { pi.on(...) }` (`examples/extensions/README.md:69-86`).
- Lifecycle: extension instances are loaded during `createAgentSession`, inline factories are added, provider registrations are applied, then `ExtensionRunner` is used by modes. Non-interactive `initializeExtensions()` wires actions and emits `session_start` (`modes/runtime-init.ts:34-41,140-141`); interactive controller emits `session_start` (`modes/controllers/extension-ui-controller.ts:248-250`); RPC/ACP do likewise (`modes/rpc/rpc-mode.ts:643-644`, `modes/acp/acp-agent.ts:2145-2147`). `session_shutdown` has a dedicated short 2s timeout (`extensibility/extensions/runner.ts:75-92`).
- Real extension example: `examples/extensions/plan-mode.ts` registers command/shortcut/flag and hooks `tool_call`, `tool_result`, `agent_end`, `session_start`, `turn_start`, `turn_end` (`plan-mode.ts:209-315,399-536`).

Q2 HOOKS/EVENTS — exact API names
- Subscribe with `pi.on(eventName, handler)`; implementation appends handlers into `extension.handlers` (`extensibility/extensions/loader.ts:119-124`). Public overloads list all supported event names (`extensibility/extensions/types.ts:929-1013`).
- Session: `resources_discover`, `session_start`, `session_before_switch`, `session_switch`, `session_before_branch`, `session_branch`, `session_before_compact`, `session.compacting`, `session_compact`, `session_shutdown`, `session_before_tree`, `session_tree`, `goal_updated` (`types.ts:951-972`; payloads in `shared-events.ts:27-139`). `session_before_switch.reason` is `new | resume | fork`; `session_switch.reason` same (`shared-events.ts:32-49`).
- Agent/turn/message: `context`, `before_provider_request`, `after_provider_response`, `before_agent_start`, `agent_start`, `agent_end`, `turn_start`, `turn_end`, `message_start`, `message_update`, `message_end` (`types.ts:972-986`; payloads in `shared-events.ts:165-198` and `types.ts:509-546`). `message_update` carries `assistantMessageEvent` for streaming deltas (`types.ts:536-540`).
- Tool execution: two surfaces exist. First, wrapper hooks `tool_call` before tool execution and `tool_result` after execution, with block/modify semantics (`types.ts:1005-1010`; `wrapper.ts:78-79,151-236`). Second, lower-level runtime events `tool_execution_start`, `tool_execution_update`, `tool_execution_end` mirror AgentEvents with args/partial/result/isError (`types.ts:549-578`; mapped in `agent-session.ts:3542-3568`).
- User/direct events: `input`, `user_bash`, `user_python`, `tool_approval_requested`, `tool_approval_resolved`, `credential_disabled`, auto-compaction/retry, TTSR and todo events are also overloads (`types.ts:986-1010`).
- Emission mapping is centralized in `AgentSession.#emitExtensionEvent`: agent_start/end, turn_start/end, message_start/update/end, tool_execution_* and auto events are transformed and emitted to ExtensionRunner (`agent-session.ts:3501-3609`). `message_update` is emitted to listeners immediately and extension dispatch is queued so UI streaming is not blocked (`agent-session.ts:2140-2145`).

Q3 MODEL-CALL TELEMETRY — where facts exist and what extensions can observe
- Canonical per-call result object is `AssistantMessage` in `packages/ai`: `api`, `provider`, `model`, optional `upstreamProvider`, `usage`, `stopReason`, `stopDetails`, `errorMessage`, `errorStatus`, `disabledFeatures`, `providerPayload`, `timestamp`, `duration`, `ttft` (`packages/ai/src/types.ts:478-512`). Extensions see this at `message_end` when `message.role === "assistant"`, and at `turn_end.message` (`types.ts:543-546`; `shared-events.ts:192-198`; emission `agent-session.ts:3536-3541,3514-3521`).
- Usage facts: `Usage` includes input/output/cacheRead/cacheWrite/totalTokens/cost and optionally premiumRequests/reasoningTokens; exact fields are used/aggregated in `SessionManager.addUsage()` (`session-manager.ts:75-100`) and exposed as `UsageStatistics` (`session-entries.ts:196-202`). Providers fill those fields and call `calculateCost(model, output.usage)`; examples: Anthropic maps `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` and calculates cost (`providers/anthropic.ts:1810-1817,2050-2062`); OpenAI Responses populates cached tokens and cost (`providers/openai-responses-shared.ts:893-895,1149-1163`); Gemini maps cached/thinking tokens and cost (`providers/google-shared.ts:709-730`).
- Model id/provider: from `AssistantMessage.provider` and `.model` (`types.ts:482-484`). Session persistence adds attribution `model?: provider/modelId[:thinkingLevel]` for assistant messages (`session-entries.ts:27-35`; `agent-session.ts:1361-1364,2343-2344`).
- Latency: provider code stamps `output.duration = Date.now() - startTime` and `output.ttft` before done/error. Examples: Bedrock (`providers/amazon-bedrock.ts:396-431`), Azure OpenAI Responses (`providers/azure-openai-responses.ts:223-235`), Cursor (`providers/cursor.ts:584-598`).
- Outcome: success/tool/length/error/abort/refusal surface through `stopReason`, `errorMessage`, `errorStatus`, and sometimes `stopDetails`. Anthropic refusal maps to error-class `stopReason` and sets `stopDetails`/`errorMessage` (`providers/anthropic.ts:2024-2044`). OpenAI Responses/Responses-shared handles refusal deltas as text content and maps terminal status to `stopReason` (`providers/openai-responses-shared.ts:695-706,893-916`). Error/abort status is in provider catch blocks (`providers/openai-completions.ts:1193-1207`; `types.ts:497-499`).
- Raw provider payload: the extension API exposes `before_provider_request` with `payload: unknown`, return type `unknown` to replace it, and `after_provider_response` with status/headers/requestId/metadata (`types.ts:509-518,833-837,973-977`). SDK wires these into Agent options as `onPayload`/`onResponse` (`sdk.ts:2429-2434`). Runner chains replacements for `before_provider_request` (`runner.ts:848-875`) and emits response metadata (`runner.ts:877-890`). Providers call `options.onPayload` after provider-specific request construction; many await replacements, e.g. Anthropic (`providers/anthropic.ts:1648-1652`), Azure Responses (`providers/azure-openai-responses.ts:142-146`), Google shared (`providers/google-shared.ts:888-892`), OpenAI Responses (`providers/openai-responses.ts:422-426`). Uncertainty/limitation: not every provider awaits or honors a replacement (Bedrock calls `options?.onPayload?.(commandInput)` without replacement at `providers/amazon-bedrock.ts:236-238`; Cursor similar at `providers/cursor.ts:2628-2630`; OpenAI completions calls without replacement at `providers/openai-completions.ts:588-590`). This is the provider-shaped request body, not guaranteed final signed HTTP bytes/headers.
- Built-in telemetry prior to extensions: `AgentLoop` starts/finishes OpenTelemetry chat spans around each LLM call and passes request details, model, response headers, and final `AssistantMessage` (`packages/agent/src/agent-loop.ts:988-1088,1107-1127`). `finishChatSpan()` applies cost, emits `ChatUsageEvent`, records stop/error status, and ends the span (`telemetry.ts:1107-1156`). `ChatUsageEvent` includes `conversationId`, `model`, `provider`, `usage`, `cost`, attributes (`telemetry.ts:233-244,1439-1449`). The CLI enables OTLP export when OTEL env vars are set (`coding-agent/src/main.ts:1164-1173`; `telemetry-export.ts:1-43,70-120`). This path is strong prior art but not itself an extension API unless the publisher runs embedded SDK with `telemetry` config.

Q4 IDENTITY — session id, file location, fork/tree/branch model
- Session IDs are minted with `Bun.randomUUIDv7()` (`session-manager.ts:59-61`). New session header includes `type:"session"`, `version`, `id`, `timestamp`, `cwd`, optional `parentSession` (`session-manager.ts:540-572`; type in `session-entries.ts:8-17`). Session file name is `<fileSafeTimestamp>_<sessionId>.jsonl` in `#sessionDir` (`session-manager.ts:571-572`).
- Default session dir is `getSessionsDir()/encoded-cwd`, where encoding is home-relative/temp-relative/legacy absolute; `computeDefaultSessionDir()` ensures and migrates the dir (`session-paths.ts:94-145`). `SessionManager.create(cwd)` uses `SessionManager.getDefaultSessionDir(cwd, ...)` (`session-manager.ts:1484-1487`). Exact root returned by `getSessionsDir()` is in `@oh-my-pi/pi-utils` outside the inspected package; practical docs/comments indicate active profile `~/.omp/.../sessions` semantics, but flag as [INFERENCE] unless you inspect pi-utils.
- Current session id/file access: `getSessionId()` and `getSessionFile()` (`session-manager.ts:970-979`); ExtensionContext exposes `ctx.sessionManager` (example uses `ctx.sessionManager.getEntries()` and `getBranch()` in `plan-mode.ts:497-526` and README `examples/extensions/README.md:131-137`).
- Tree model: every non-header `SessionEntry` has `id`, `parentId`, `timestamp` (`session-entries.ts:27-30`). `SessionEntryIndex` stores `entriesById`, parent→children adjacency, labels, active leaf, and usage (`session-manager.ts:112-119,141-143,181-208`). `buildSessionContext()` walks from leaf to root following `parentId` to build active branch (`session-context.ts:65-130`). `SessionTreeNode` is `{ entry, children, label? }` (`session-entries.ts:188-194`).
- Resume/open: `setSessionFile()` loads entries, applies header id into `#sessionId`, and if header cwd differs, repoints cwd/sessionDir to that file’s project (`session-manager.ts:700-732`). `SessionManager.open(filePath)` creates a manager and calls `setSessionFile()` (`session-manager.ts:1531-1547`).
- Fork current session: `AgentSession.fork()` emits `session_before_switch`/`session_switch` with reason `fork`, flushes, calls `sessionManager.fork()`, copies artifacts, and syncs provider/session id (`agent-session.ts:6216-6268`). `SessionManager.fork()` creates a fresh session id/file and header whose `parentSession` is the previous session id, while preserving entries (`session-manager.ts:765-790`). Note: parentSession here is an id, not a file path.
- Branch from a user entry: `AgentSession.branch()` emits `session_before_branch`, then either `newSession({ parentSession: previousSessionFile })` when branching from root or `createBranchedSession(selectedEntry.parentId)` for a pruned branch (`agent-session.ts:10770-10820`). `createBranchedSession()` writes a fresh session with only the path to `leafId`, and header `parentSession` is the source session file path when persisted (`session-manager.ts:1407-1425`). Note the mixed parent linkage semantics: `fork()` stores parent id, `createBranchedSession()` stores parent file path, `forkFrom()` stores source header id (`session-manager.ts:1492-1518`). Later implementer should normalize this in ledger ingestion.

Q5 IMPORTS — npm/workspace packages and constraints
- Current extension loader is native Bun import via `loadLegacyPiModule()`, not an actual jiti call in the implementation. `loadExtension()` calls `loadLegacyPiModule(resolvedPath)` (`loader.ts:289-311`); `loadLegacyPiModule()` installs a Bun plugin for legacy specifier rewrites and imports the real path with `?mtime=` cache busting (`plugins/legacy-pi-compat.ts:635-645`). The Changelog/README mention “jiti” and deps examples, but code path is Bun import + scoped `Bun.plugin` rewrite.
- Extension source graph runs in place: `import.meta.url` is the real file, and native module resolution starts from the extension file/package (`legacy-pi-compat.ts:623-644`). Legacy specifiers like old `pi-*` and `@sinclair/typebox` are rewritten only for files in the extension source graph; unrelated node_modules and project source are not matched (`legacy-pi-compat.ts:600-620,656-720`).
- NPM deps: supported if resolvable by Bun from the extension location. Examples: `with-deps/package.json` declares `omp.extensions` and dependency `ms` (`examples/extensions/with-deps/package.json:1-13`); `chalk-logger.ts` imports `chalk` from parent node_modules (`examples/extensions/chalk-logger.ts:1-8`).
- OMP package imports: extension examples import types from `@oh-my-pi/pi-coding-agent`, and package exports expose source `.ts` paths (`examples/extensions/README.md:74-76`; `package.json:520-578`).
- Importing `~/agents/packages/control-plane`: there is no current `packages/control-plane` in this workspace (find returned no package). If a later packet adds it as a workspace package under root `workspaces: ["packages/*", "apps/*"]` (`~/agents/package.json:1-8`), a bare package import will only work from an extension path whose Bun resolution can see `~/agents/node_modules`/workspace links, or if the package is installed/linked into the extension’s own package. If the extension lives in `~/.omp/agent/extensions`, bare imports from `~/agents/packages/control-plane` are not guaranteed; use an absolute/relative file import, package the extension under `~/agents` and load by absolute path in settings/CLI, or add the control-plane package as a dependency of the extension package and run `bun install` so Bun can resolve it. Avoid relying on vendor/oh-my-pi’s workspace because it is a separate package tree.

Q6 PRIOR ART — telemetry/observability/export paths
- OpenTelemetry is built in at agent-core level: `AgentTelemetryConfig` has `costEstimator`, `onCostDelta`, `onChatUsage`, provider/model normalizers, agent identity (`telemetry.ts:351-367`); `ChatUsageEvent` exposes per-step model/provider/usage/cost (`telemetry.ts:233-244,1439-1449`). CLI registers OTLP/proto exporter from env and sets `sessionOptions.telemetry = {}` when enabled (`main.ts:1164-1173`; `telemetry-export.ts:70-120`). Publisher can piggyback conceptually, but extensions cannot currently set `sessionOptions.telemetry` from inside the extension after session creation.
- TUI/status usage path aggregates persisted assistant message usage from session entries. `Footer` totals input/output/cacheRead/cacheWrite/cost/premiumRequests from assistant messages (`modes/components/footer.ts:119-135`). Status line reads `sessionManager.getUsageStatistics()` and renders token_total, cost, cache_read, cache_write (`modes/components/status-line/component.ts:559-570`; `segments.ts:329-370,455-480`). This is good logic to mirror for reconciliation.
- Session manager maintains branch-aware aggregate usage from assistant messages and task tool results (`session-manager.ts:75-100,193-194,946-947`). This can seed/reconcile a ledger on `session_start` by walking `ctx.sessionManager.getEntries()/getBranch()`.
- There is a snapcompact savings JSONL journal recording session/provider/model/toolCallId/savedTokens, showing a simple fire-and-forget local telemetry precedent (`session/snapcompact-savings-journal.ts:8-12` from search result). ACP also builds turn usage deltas from `getUsageStatistics()` baselines and maps stop reasons for clients (`modes/acp/acp-agent.ts:622-750,1144-1146,1234-1238,1725-1756`).

Recommended publisher shape
- Put the publisher as a real extension package under `~/agents` (for example `packages/control-plane-omp-publisher` or inside the future control-plane package) with `package.json { "type":"module", "omp": { "extensions": ["./src/omp-extension.ts"] } }`, then load it via absolute path in project `.omp/settings.json#extensions` or CLI `-e`. This keeps Bun resolution near the workspace/control-plane package and avoids relying on `~/.omp/agent/extensions` resolving `~/agents` workspace imports.
- Hooks to use: `session_start` to upsert session row and replay existing branch/file entries; `message_end` filtered to roles user/assistant/toolResult/custom for turns/events and final assistant model_call facts; `turn_start`/`turn_end` for turn boundaries; `tool_execution_start`/`tool_execution_end` plus `tool_call`/`tool_result` if ledger wants both model-requested tool calls and actual execution outcomes; `before_provider_request`/`after_provider_response` for request/response metadata when available; `session_switch`, `session_branch`, `session_tree`, `session_shutdown` for session/fork/tree lifecycle. Map `AssistantMessage` at assistant `message_end` to `model_calls`: provider/model/api/upstreamProvider, usage.{input,output,cacheRead,cacheWrite,totalTokens,cost,total,premiumRequests,reasoningTokens}, duration/ttft/timestamp, stopReason/stopDetails/errorMessage/errorStatus. Use session header/id/file plus entry `id`/`parentId` to map `sessions` and turn lineage. Flag in implementation: parentSession has mixed id/file semantics across fork/branch, and raw provider payload replacement is provider-dependent; record nullable raw_request_payload with provider support marker rather than assuming universal capture.
