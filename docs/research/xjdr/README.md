## Synthesis: xjdr's stack and what it implies for a local agent control plane

**Stack as described.** A single-dev, vertically integrated loop: custom SCM ("ncode scm") = jj for draft state with a real jj-native persistence layer/backend + sapling for stacked commits, shallow virtual checkouts (instant clones, nothing pulled to disk), cloud-synced workspaces, per-file ACLs, agents and reviewers as first-class citizens — explicitly modeled on Google CITC/Meta EdenFS practice. On top: a Claude-Code-fork harness (now the open-sourced ncode TUI — event-based REPL, Rust N-API markdown renderer and OpenAI-compat WebSocket client, tmux/PTY-native), his own inference platform (bespoke Rust/gRPC serving layer, disagg prefill/decode, KV-cache pooling, per-token tracing), and OSS models (GLM 5.2 / Kimi 2.7 / dsv4-flash tiered opus/sonnet/haiku) fine-tuned onto the harness. Orchestration idioms: named work streams, tmux panes/windows for long-running resumable agents, push-to-wake instead of polling, one harness testing another, models "promoted" to SRE roles running ops.

**Stated pain points.** git/GitHub break at dozens-to-hundreds of concurrent agents (stale branches/worktrees, conflict storms, dirty state, clone/env-setup cost, IOPS); review/merge becomes the human bottleneck past ~10 parallel sessions; next wall is random disk I/O forcing multi-machine agents that must look single-machine; harness dependence on one vendor is a systemic risk; frontier-harness fragility (codex freezing, >5 subagents crashing); noisy neighbors (1M-ctx spammers) wrecking TTFT; slop/complexity explosion requiring periodic attic/ rewrites.
